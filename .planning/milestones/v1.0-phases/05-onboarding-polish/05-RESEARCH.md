## Summary

Phase 5 is a polish-and-wrap phase, not a feature phase. The app is fully functional. This phase gates first-launch users through a 3-screen onboarding flow, adds per-tier empty states, migrates hardcoded colors and font sizes to semantic system values, and audits accessibility across all existing views.

The critical implementation question is the **onboarding gate pattern**: `@AppStorage` in `VitaminGApp.body` is the correct approach. The existing `VitaminGApp.init()` wires `ModelContainer` and `AppRouter`; the `body` computed property is where the gate lives — it reads `@AppStorage("hasCompletedOnboarding")` and conditionally presents either `OnboardingView` (a `NavigationStack`) or `ContentView`. No changes to `init()` are needed.

The secondary concern is the **Dynamic Type migration**. The codebase uses `.system(size: N, weight: .X, design: .rounded)` pervasively in five views: `GoalDetailView`, `GoalRowView`, `ProfileView`, `ProfileEditSheet`, and `StatsView` (one fixed-size label in `TierStatCard`). The migration is mechanical but must preserve `.fontDesign(.rounded)` — the correct modern idiom is `.font(.body.weight(.semibold)).fontDesign(.rounded)` rather than chaining `.fontDesign` as a view modifier in some contexts.

The **Dark Mode color audit** has one root cause: `Color(red: 0.949, green: 0.949, blue: 0.969)` used as a screen background in `EmptyStateView` and `GoalDetailView`. The fix is `Color(.systemGroupedBackground)` — already used correctly in `StatsView` and `ProfileView`. `Color(.systemBackground)` is already used in card surfaces in `GoalDetailView` and `ProfileView`. The completion green `Color(red: 0.063, green: 0.725, blue: 0.506)` is sufficiently saturated to read in both modes (no change needed).

**Primary recommendation:** Implement in this order: (1) OnboardingView + gate in VitaminGApp, (2) NotificationPermissionSheet, (3) per-tier empty states, (4) Dynamic Type migration, (5) Dark Mode color fixes, (6) accessibility audit, (7) app icon + launch screen.

## Architecture Patterns

### Onboarding Gate in VitaminGApp

The gate belongs in `VitaminGApp.body`, not `init()`. `@AppStorage` is a property wrapper that is reactive in SwiftUI's rendering cycle — placing it in `body` means the view automatically transitions when the value changes.

```swift
// Source: VERIFIED codebase audit of VitaminGApp.swift + @AppStorage SwiftUI behavior [ASSUMED: exact syntax]
@main
struct VitaminGApp: App {
    // ... existing init() unchanged ...

    @AppStorage("hasCompletedOnboarding") private var hasCompletedOnboarding = false

    var body: some Scene {
        WindowGroup {
            if hasCompletedOnboarding {
                ContentView()
                    .modelContainer(container)
                    .environment(router)
            } else {
                OnboardingView()
                    .modelContainer(container)   // needed for screen 3 (AddGoalView)
                    .environment(router)
            }
        }
    }
}
```

**Critical:** `OnboardingView` must receive `.modelContainer(container)` because screen 3 embeds `AddGoalView` which calls `viewModel.addGoal(context: modelContext)`. Without the container in the environment, screen 3 will crash at goal creation. [VERIFIED: AddGoalView.swift reads `@Environment(\.modelContext)`]

**AppStorage key must be set to `true` BEFORE dismissal** — set it in the completion handler of screen 3's save action (or "Maybe later" tap), not on `OnboardingView.onDisappear`. Setting it in `onDisappear` races with the view transition. [ASSUMED: based on SwiftUI property wrapper timing behavior]

### OnboardingStep Enum — Type-Safe NavigationStack Routing

```swift
// Source: D-02 locked decision + AppRoute.swift pattern [VERIFIED: codebase]
enum OnboardingStep: Hashable {
    case welcome
    case tiers
    case createGoal
}
```

`OnboardingView` is a `NavigationStack` with a path starting at `.welcome`. Each screen is reached via `navigationDestination(for: OnboardingStep.self)`. This matches the existing `AppRoute` / `NavigationStack` pattern in `ContentView.swift` and `AppRouter.swift`. [VERIFIED: ContentView.swift, AppRoute.swift]

```swift
// Pattern (matches existing app convention)
struct OnboardingView: View {
    @State private var path: [OnboardingStep] = []
    @AppStorage("hasCompletedOnboarding") private var hasCompletedOnboarding = false

    var body: some View {
        NavigationStack(path: $path) {
            WelcomeScreen(path: $path, onSkip: finish)
                .navigationDestination(for: OnboardingStep.self) { step in
                    switch step {
                    case .welcome:
                        WelcomeScreen(path: $path, onSkip: finish)
                    case .tiers:
                        TiersScreen(path: $path, onSkip: finish)
                    case .createGoal:
                        CreateFirstGoalScreen(path: $path, onComplete: finish)
                    }
                }
        }
    }

    private func finish() {
        hasCompletedOnboarding = true
    }
}
```

**Back navigation is free** — `NavigationStack` handles back button + swipe-back automatically. No `.fullScreenCover` per D-02. [VERIFIED: D-02 locked decision]

### Per-Tier Empty States

The existing `GoalListView` shows a **global** `EmptyStateView` when `goals.isEmpty`. Per D-06, each tier section needs its own empty state when `tieredGoals.isEmpty`. The `TierSectionView` already iterates `GoalTier.ordered` and filters goals; the guard currently skips rendering when a tier has zero goals. Replace that guard with empty state rendering:

```swift
// Source: GoalListView.swift lines 108-119 [VERIFIED: codebase]
// Current: tieredGoals.isEmpty → section omitted
// Phase 5: tieredGoals.isEmpty → TierEmptyStateView(tier: tier, onAdd: ...)
ForEach(GoalTier.ordered, id: \.self) { tier in
    let tieredGoals = goals(for: tier)
    TierSectionView(tier: tier) {
        if tieredGoals.isEmpty {
            TierEmptyStateView(tier: tier) { showingAddGoal = true }
        } else {
            ForEach(tieredGoals) { goal in goalRow(for: goal) }
        }
    }
}
```

The global `EmptyStateView` (shown when ALL goals are empty) is still valuable as the very-first-launch state before any tier sections render. Keep it for the `!hasAnyGoals` branch. The per-tier states are additive inside the list body. [VERIFIED: GoalListView.swift]

**`@Query` note:** `@Query` returns a flat array — the tier filtering is done by `goals(for:)` computed property which calls `GoalSorter.sort(goals, by: sortOption)` then `.filter { $0.tier == tier }`. The per-tier empty state only appears in `.byTier` sort mode (the `else` branch in `goalList`). In `.byCompletionStatus` mode, the two-section (Active/Completed) layout remains unchanged. [VERIFIED: GoalListView.swift lines 88-123]

### Notification Permission Sheet — Medium Detent

```swift
// Source: D-04 locked decision. SwiftUI .presentationDetents available iOS 16+ [ASSUMED: exact syntax]
.sheet(isPresented: $showingNotificationPermission) {
    NotificationPermissionSheet(onAllow: {
        Task { await NotificationScheduler.shared.requestAuthorization() }
        showingNotificationPermission = false
    }, onNotNow: {
        showingNotificationPermission = false
    })

    .presentationDragIndicator(.visible)
}
```

`.presentationDetents([.medium])` is the SwiftUI-native API for half-sheet on iOS 16+. No `UISheetPresentationController` bridging required. [ASSUMED: API availability at iOS 16+ matches project minimum iOS 17]

**Where to trigger:** Present after `hasCompletedOnboarding` is set to `true` in the `finish()` action. A `@State private var showingNotificationPermission = false` in `OnboardingView`, set to `true` in `finish()`, drives the sheet. The sheet is presented over `ContentView` once `OnboardingView` has dismissed. Alternatively, present from `CreateFirstGoalScreen` directly after goal save — simpler and avoids cross-view-boundary state. D-04 says "after first goal is created (or after the onboarding flow if skipped)." [VERIFIED: D-04 locked decision]

**Check authorization first:** Before showing the sheet, call `NotificationScheduler.shared.authorizationStatus()`. If already `.authorized` or `.denied`, skip the sheet. Only show for `.notDetermined`. [VERIFIED: NotificationScheduler.authorizationStatus() exists in NotificationScheduler.swift]

### Dynamic Type Migration

The correct idiom for `.fontDesign(.rounded)` with semantic fonts in iOS 17+ SwiftUI:

```swift
// Source: [ASSUMED — Apple SwiftUI font API]
// OLD (fixed size, no Dynamic Type):
.font(.system(size: 16, weight: .regular, design: .rounded))

// NEW (semantic + rounded):
.font(.body)
.fontDesign(.rounded)

// NEW with weight:
.font(.body.weight(.semibold))
.fontDesign(.rounded)

// Or chained (equivalent):
.font(.system(.body, design: .rounded, weight: .semibold))
```

`.font(.system(.semanticStyle, design: .rounded, weight: .weight))` is a single-call form available in iOS 16+. Since project minimum is iOS 17, this is safe. [ASSUMED: API syntax — verify against Apple docs before use]

## Common Pitfalls

### Pitfall 1: Onboarding `NavigationStack` Missing `.modelContainer`
**What goes wrong:** `CreateFirstGoalScreen` embeds `AddGoalView`. `AddGoalView` reads `@Environment(\.modelContext)`. If `OnboardingView` doesn't receive `.modelContainer(container)`, goal creation crashes with a nil context error.
**Why it happens:** Developers assume the app-level container propagates through the condition branch.
**How to avoid:** In `VitaminGApp.body`, apply `.modelContainer(container).environment(router)` to BOTH the `if` and `else` branches, or apply it to the parent container that wraps the condition. [VERIFIED: VitaminGApp.swift and AddGoalView.swift]
**Warning signs:** Crash on tap of "Save" in screen 3 of onboarding.

### Pitfall 2: Setting `hasCompletedOnboarding = true` Too Late
**What goes wrong:** If set in `onDisappear` of `OnboardingView`, it races with the SwiftUI view transition and may fire after the next render cycle, causing a flash.
**How to avoid:** Set it synchronously in the `finish()` action function, before any navigation. Since `@AppStorage` is backed by `UserDefaults`, the write is synchronous. The `body` re-renders in the next run loop tick.
**Warning signs:** Brief re-appearance of onboarding after "done."

### Pitfall 3: Per-Tier Empty States Appear in `.byCompletionStatus` Sort Mode
**What goes wrong:** The tier-section loop is inside the `else` branch of `if sortOption == .byCompletionStatus`. If you add empty states inside `TierSectionView`, they correctly only appear in `.byTier` mode. But if the empty state logic is placed outside, it could render in both modes.
**How to avoid:** Empty states for tiers belong exclusively inside the `ForEach(GoalTier.ordered)` loop, which is already in the `else` branch. [VERIFIED: GoalListView.swift lines 107-119]

### Pitfall 4: Dynamic Type Breaking `.fontDesign(.rounded)` Convention
**What goes wrong:** Using `.font(.body).fontDesign(.rounded)` as a chained modifier should work, but some early SwiftUI versions had issues with modifier ordering. The safe form is `.font(.system(.body, design: .rounded))`.
**How to avoid:** Prefer `.font(.system(.body, design: .rounded, weight: .regular))` for complete control, or verify `.fontDesign(.rounded)` renders correctly on target iOS 17 simulator.
**Warning signs:** Font reverts to system default design (San Francisco) despite `.fontDesign(.rounded)`.

### Pitfall 5: `@AppStorage` in `init()` Instead of `body`
**What goes wrong:** `@AppStorage` can be declared as a stored property but it won't be reactive if not in a `View` or `App` context. In `App.body`, it correctly drives re-renders when the value changes.
**How to avoid:** Declare `@AppStorage("hasCompletedOnboarding")` as a property of the `VitaminGApp: App` struct (not inside `init()`), and evaluate it in `body`. [VERIFIED: VitaminGApp.swift structure]

### Pitfall 6: Notification Sheet Shown When Already Authorized
**What goes wrong:** If the user already granted notification permission (e.g., was previously authorized from SettingsView's "Enable Notifications" button), showing the permission sheet is confusing and wastes a permission dialog.
**How to avoid:** In `OnboardingViewModel` or the `finish()` handler, call `NotificationScheduler.shared.authorizationStatus()` and skip the sheet presentation if status is `.authorized` or `.denied`. [VERIFIED: NotificationScheduler.authorizationStatus() exists]

### Pitfall 7: `Color.white` Card Surfaces in Dark Mode
**What goes wrong:** `GoalDetailView` uses `Color.white` for card backgrounds (lines ~82, ~126, ~180). In Dark Mode, these render as blindingly bright white cards on a dark background.
**How to avoid:** Replace `Color.white` with `Color(.systemBackground)` in any card surface that is NOT a gradient or intentionally high-contrast element. Already done correctly in `ProfileView`. Note: `GoalDetailView.headerSection` uses `Color(.systemBackground)` — but `quoteCardSection` uses `goal.tier.color.opacity(0.10)` which adapts acceptably. [VERIFIED: GoalDetailView.swift lines 82, 126, 180 use `Color(.systemBackground)` — already correct. The only remaining fix is the `.background(Color(red: 0.949,...))` on the scroll view itself.]

## Open Questions

1. **Notification sheet timing: in-flow vs. post-flow**
   - What we know: D-04 says "after first goal is created (or after the onboarding flow if skipped via 'maybe later')."
   - What's unclear: Should the sheet be presented from inside `CreateFirstGoalScreen` (immediate after save) or from `OnboardingView.finish()` (a few milliseconds after the transition to ContentView begins)?
   - Recommendation: Present from `CreateFirstGoalScreen` after save — it's simpler and avoids cross-view state. If "maybe later" is tapped, the gate sets `hasCompletedOnboarding = true` and the sheet is never shown until user re-runs onboarding (which is deferred to v2 anyway). This satisfies NOTIF-01 since neither path fires on cold launch.

2. **`AddGoalView` reuse vs. minimal embed in screen 3**
   - What we know: D-03 says "embed a minimal version of AddGoalView or navigate to it." `AddGoalView` is a full `NavigationStack` + `Form` with Cancel/Save toolbar. It is currently presented as a `.sheet` in `GoalListView`.
   - What's unclear: Should screen 3 reuse `AddGoalView` as a child (removing its `NavigationStack` wrapper to avoid nested NavigationStacks) or recreate a simpler form?
   - Recommendation: Reuse `AddGoalView`'s internal `Form` content without its `NavigationStack` wrapper. Extract the form sections into a shared subview if needed. Nested `NavigationStack` is a known SwiftUI gotcha that causes double-navigation-bar rendering.

3. **StatsView streak numeral exception scope**
   - What we know: D-09 explicitly exempts AvatarView initials and "tier icon sizes that are layout-fixed."
   - What's unclear: Whether `Text("\(streak)")` at `size: 28` and `size: 48` in stats cards is intended to be Dynamic Type responsive.
   - Recommendation: Treat the large stat numbers as display-proportional (same reasoning as AvatarView) and leave them fixed, but migrate everything else in StatsView. Document the exception with a comment.
